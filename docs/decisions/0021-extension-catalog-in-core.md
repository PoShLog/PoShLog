# 0021 — Core lists and installs its extensions from a catalogue built into the assembly

- **Status:** proposed
- **Date:** 2026-11-03

## Context

PoShLog 3 has eight first-party extensions in `extensions/` (four refreshed, four new sinks). A user who wants to log
to Seq or Elastic has to know the module name, find it on the Gallery and know that during the preview it installs
only with `Install-PSResource -Prerelease` ([ADR 0019](0019-extensions-ship-as-prereleases-during-the-core-3-preview.md)).
Tomáš asked for a Core command that lists the extensions and installs them (approved 2026-11-03).

Constraints:

- The list must not go stale when an extension is added, renamed or gets a new version.
- Listing must work offline; only an explicit online check may reach the Gallery.
- Installing must work non-interactively (CI, scheduled jobs) and follow the preview rules of ADRs 0017 and 0019.
- Only first-party extensions are installed. Other authors' modules are checked but not endorsed
  ([ADR 0009](0009-first-party-sinks-third-party-check-non-blocking.md)).

## Decision

Core gets two cmdlets, `Get-PoShLogExtension` and `Install-PoShLogExtension`.

- **Catalogue.** The build embeds every `extensions/*/*.psd1` and Core's own `src/PoShLog.psd1` into
  `PoShLog.Core.dll` as resources. At run time Core reads them with the PowerShell parser (the same safe, data-only
  evaluation as `Import-PowerShellDataFile`). Each entry gets its name, version and prerelease label, the exported
  commands, the supported platforms (from the `Windows`/`Linux`/`MacOS` tags), the project URL, and a one-line summary:
  the lines of the manifest's `Description` after the first, up to the first blank line. Nothing is kept by hand; a new extension directory is in the
  next Core build.
- **Listing.** `Get-PoShLogExtension [-Name <wildcard>]` returns the catalogue with the installed version (the newest
  from `Get-Module -ListAvailable`). It needs no network. `-Online` adds the latest Gallery version through
  `Find-PSResource`, with `-Prerelease` under the rule below, and `-Repository` picks the repository.
- **Installing.** `Install-PoShLogExtension -Name <name>` calls `Install-PSResource` from PSResourceGet, which ships
  with PowerShell 7.4. It passes `-Prerelease` when this Core build is a prerelease, or when `-Prerelease` is given,
  and passes `-Scope`, `-Repository`, `-TrustRepository` and `-PassThru` through. It supports `-WhatIf` and `-Confirm`
  and accepts names from the pipeline (`Get-PoShLogExtension | Install-PoShLogExtension`). Names outside the catalogue
  are an error. `-Name` is mandatory: an interactive host prompts for it, and no menu is built.
- **Platforms.** Installing an extension whose tags do not list the current OS writes a warning and continues.

## Alternatives considered

- **A hand-kept list in C#.** Simple, but it goes stale with every new extension or version, the problem the brief
  names first.
- **A JSON catalogue generated by a build script.** Generating needs `pwsh` inside `dotnet build`, and a committed
  generated file needs a staleness test. Embedding the manifests needs neither and cannot drift.
- **Searching the Gallery by tag or prefix** (`Find-PSResource PoShLog.*`). Always current, but needs the network
  even to list, and it returns other authors' modules, which ADR 0009 does not endorse.
- **A separate catalogue field in each manifest** (`PrivateData.PoShLog.Summary`). More explicit, but repeats what
  `Description` says. The descriptions get a clean second line instead, which also reads better on the Gallery.
- **Install-Module (PowerShellGet 2).** It cannot resolve the prerelease dependency of a preview extension
  (ADR 0017).
- **An interactive menu when `-Name` is missing.** Useful at a console, but it is code that cannot run in CI, and the
  mandatory-parameter prompt already covers the console case.

## Consequences

- A Core build lists the extensions as they were in the same commit. A Core release that predates a new extension does
  not list it; `-Online` shows newer versions of the listed ones only.
- The manifests' `Description` keeps the shape "first line: what PoShLog is; the lines after it, up to a blank line:
  what this extension does". A test checks every summary, the commands and the embedded Core version.
- Enrichers lists its functions in `FunctionsToExport` instead of `'*'`, so the catalogue can name its commands.
- Installing requires PSResourceGet. Without it, the command fails with a message that names the module.
- When Core 3.0.0 ships as stable (ADR 0017's release commit), the automatic `-Prerelease` stops by itself.
